先把对象分清：source、input asset、serving object 不是一回事

三层对象模型

企业里最常见的混乱，不是“没资源”，而是把原始资源、输入资产和服务对象混成一层。

先把三层对象看清。下一页再讲混层以后会怎么坏，最后一页再把每层回答的问题讲清。

这三层一旦混了，会怎样

这三层一旦混了，会怎样
  • 把原始资源直接当输入资产：后面写不出稳定 contract
  • 把输入资产直接当服务对象：Week03 ingest 边界持续漂移
  • 以为“数据库里那张表”天然就是 AI 输入：引用、过滤、权限都会跟着漂

再把这三层对象各自回答什么问题讲清

对象 真正回答的问题
source system / raw resource 世界原貌是什么
input asset 什么值得接、怎么接、谁负责
serving object 下游如何稳定消费

一套可复用的方法：发现资源 → 资格审查 → 消费映射

对象建模主方法

发现资源 世界里有什么

→

资格审查 有没有资格成为输入资产

→

消费映射 后续谁来消费它

盘点的终点不是“登记完成”，而是形成消费路径。消费路径不清，后面的 metadata、contract、manifest 都会悬空。

先把三件事立住
  • 发现资源：先把候选对象找出来，不急着宣布接入
  • 资格审查：不是所有资源都应该立刻进系统
  • 消费映射：只有明确后续消费者，盘点才真正进入工程链

资格审查永远问四个问题：事实、证据、边界、责任

事实是什么

主键、状态、时间、版本是不是稳定。

证据是什么

以后引用它时，能不能回到原处。

边界是什么

谁能看、谁能搜、哪些字段必须脱敏。

责任是什么

谁拥有口径、谁更新、出了问题谁拍板。

真正有用的盘点表，不是三列，而是四组字段

组别 代表字段 真正作用
身份与事实组 asset_id / asset_name / asset_class / business_fact / source_system 它到底是谁，承载什么业务事实
责任与更新组 owner / update_mode / freshness_expectation 谁负责，它怎么更新
边界与风险组 access_scope / pii_level / risk_tags 谁能看、谁能入模、风险在哪
消费与接入组 candidate_consumers / evidence_locator / admission_status / notes 谁消费它，为什么 ready / hold / exclude

再把这四组字段讲口语化一点

身份与事实组

先回答“它到底是谁，承载哪种业务事实”。

责任与更新组

先回答“谁负责，它是全量、增量还是版本替换”。

边界与风险组

先回答“谁能看、谁能送进模型、最先要盯的风险是什么”。

消费与接入组

先回答“后面谁消费它，以及为什么现在 ready / hold / exclude”。

企业盘点最容易失败，不是因为不会列，而是做了三种假动作

只列资源目录

看起来得到一张完整清单，但两周后还是写不出稳定 contract。

只写字段说明

字段解释很细，owner、边界、消费关系还是不清楚。

不写资格判断

什么都接、什么都想试，最后 ingest 入口和权限边界一起漂。

Ticket 资产：最容易被误以为“天然可接”

重点列
重点列 目的
ticket_id / status / priority 保住事实主键和状态口径
tenant_id / owner_team 保住边界和责任
created_at / updated_at 保住时间窗和增量起点
最常见误判
  • 把评论流和主工单事实混成一层
  • 没有 tenant_id 还想做跨租户检索
  • 只写字段，不写 admission 判断

Document 资产：版本、章节和定位不清，后面就没法 citation

重点列
重点列 目的
doc_id / doc_version 保住版本身份
page_no / section_path 保住引用回指
access_scope / pii_level 保住过滤和权限
最常见误判
  • 正文在，但版本不在
  • 能检索，不能 citation
  • 只记文件名，不记章节定位

Audio 资产：只有 transcript，没有时间锚点，责任就会漂

重点列
重点列 目的
call_id / speaker_role 保住对话角色
start_ts / end_ts 保住证据切片
redaction_flag / pii_level 保住隐私边界
最常见误判
  • 只有 transcript，没有时间锚点
  • 角色错位导致责任判断漂移
  • 脱敏在下游补，已经晚了

Video 资产：分段、OCR 和发布边界必须在盘点阶段就立住

重点列
重点列 目的
video_id / segment_ts 保住片段边界
frame_ts / ocr_text 保住画面证据
access_scope / release_status 保住发布和使用边界
最常见误判
  • 把整段视频当单个对象
  • OCR 出来就当事实，不做核验
  • 公开视频和内部培训视频不分级

不是所有资产都该立刻接入：先做分层准入

分层
分层 进入条件 典型动作
ready_now 事实、证据、边界、责任都基本清楚 进入 Week03 ingest baseline
conditional 价值高，但还缺一两个关键条件 补 owner / 证据 / 权限后再接
hold 暂时不稳，但未来可能接 留在 inventory，先不接入
exclude 高风险或价值不成立 明确写出不接原因

→

→

把本地动作翻译回方法论

本地动作 方法论含义
先写 asset_class 先把输入对象分型，而不是先堆字段
写 source_system 把世界原貌和系统对象建立映射
写 owner / access_scope 先把责任和边界写进对象
写 evidence_locator 提前为 citation / tracing 留锚点
写 candidate_consumers 让对象从一开始就面向未来消费方
写 admission_status 把盘点从登记动作切成准入判断
在 notes 写原因 让后续 contract / manifest 有判断依据

行业信号与下一讲：盘点之后，真正被系统消费的是 metadata 接口

OpenMetadata

资产视图不再只有 schema，owner、lineage、usage、quality 已经是对象定义的一部分。

OpenLineage

运行时对象正在被 dataset / job / run 重新组织，说明“对象边界”会直接影响后续治理和追踪。

Azure AI Search

多模态检索越来越依赖明确的输入对象和 metadata，而不是“先接进来再慢慢补”。
