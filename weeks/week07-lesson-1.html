Week 7｜课时1｜为什么“抽出文本”不等于非结构化数据工程

不是把 PDF 变成文本，而是把文档变成可追溯的数据资产

这一讲先立住 Week7 的核心判断：

非结构化数据工程的产出不是一堆 text chunks，而是能被检索、引用、质检和回放的 document asset。

进入课时 2 返回 Week7 总览

下载讲义

提供适合离线阅读的 PDF 版和适合批注整理的 Word 版。

PDF 版 · 打印 / 离线阅读 Word 版 · 批注 / 二次整理

这节课解决什么问题

Week03 已经能把文档拿进系统，但这还不等于 Week08 可以安全检索。

如果解析阶段只留下纯文本，下游会立刻遇到这些问题：

  • 表格被打散，字段和含义断开
  • 标题层级丢失，chunk 不知道自己属于哪个 section
  • 页码和 bbox 丢失，citation 无法回指原文
  • 解析策略变化后，坏案例无法复盘
  • 质量不合格的 chunk 被直接送进索引

所以 Week7 的目标是把 raw document 升级成：

parsed document + knowledge sections + document chunks + evidence anchors + quality gate。

先用大白话讲

如果你是第一次接触非结构化数据工程，可以把 PDF to text 想成：把一本维修手册的每一页都撕下来，再揉成一团文字。文字还在，但目录、页码、表格、图片位置、版本和来源都不可靠了。

RAG 真正需要的不是“文字堆”，而是一张张证据卡片：这段话来自哪份手册、哪一章、哪一页、哪个表格、哪个版本，质量是否过关，是否允许进入索引。

在 OmniSupport 里，Northstar Edge Gateway 安装手册里的接线图、错误码表和故障排查步骤如果只保留正文，后续回答很容易“看起来对”，但引用不稳、表格错配、版本不可复盘。

技术内涵：非结构化数据工程到底工程化了什么

工程化对象 为什么重要 缺了会怎样 OmniSupport 例子
文档形状 layout、reading order、heading hierarchy 决定读者怎么理解文档 标题和正文混成一团，chunk 不知道自己属于哪个问题 Help Center 的 SSO 排障章节被切到错误主题下
文档位置 page_no、bbox、section_path、source_url 决定能否回指原文 citation 无法定位，用户质疑时只能全文搜索 Edge Gateway PDF 回答了错误码，却找不到页码
文档版本 source_fingerprint、doc_version、parse_strategy_version 支撑复盘 文档更新后无法证明当时回答引用的是哪版 Release Notes v1/v2 的变更说明被混用
文档质量 empty chunk、orphan chunk、anchor coverage、bbox coverage 决定能否索引 Week8 更快找到坏资料，而不是更稳回答 空 chunk 或无 anchor chunk 被建索引
消费边界 allowed_for_indexing 决定 Week8 能不能消费 warn/fail/quarantine 混在一起，索引准入失控 week8_ready_gate.json 只写 pass，不写原因

外延边界：这节课不讲什么

不讲什么 为什么以后会用到 本周只做什么
embedding Week8 会把合格 chunk 写入索引 先保证 chunk 有结构、证据和质量状态
RAG API Week8 response 会展示 citation 先生成 evidence anchor，禁止 LLM 临时拼 citation
OCR / VLM 生产化 扫描件和图片文档最终会需要更强能力 Student Core 只记录 capability 和 missing reason
完整治理 Week14 会处理 release / audit / governance 先保留 fingerprint、version、license_tag 和 quality flags

先看一张总图

1. “抽出文本”为什么不够

很多 RAG demo 会把文档处理简化成：

PDF -> text -> chunks -> embeddings

这条链路最大的问题不是“效果不够好”，而是工程对象不完整。它没有回答：

  • 这段文字来自哪个文件版本？
  • 来自第几页、哪个标题层级？
  • 如果是表格，表头和行列关系还在不在？
  • 这个 chunk 是否有证据锚点？
  • 解析策略变更后，坏案例能不能复现？
Important核心判断

非结构化数据工程不是抽文本，而是把文档变成可追溯、可质检、可版本化、可供检索消费的数据资产。

2. Week7 的对象边界

对象 它是什么 不是 Week8 需要它做什么
raw document 原始文件或对象存储路径 已可检索内容 提供可校验的 raw bytes 和 source_fingerprint
parsed document 带布局和层级的解析结果 一串无结构文本 保留 page、bbox、table、heading 等 provenance
knowledge section 文档结构单元 最终检索 chunk 让 chunk 继承标题层级和上下文
document chunk Week8 索引候选单元 生成阶段的 citation 成为可过滤、可质检、可索引的最小证据单元
evidence anchor 回指原文位置的证据对象 LLM 临时拼接的 URL 成为 citation 的唯一事实来源
quality gate Week8 准入判断 人工随便看几个样本 决定哪些 chunk allowed_for_indexing=true

3. PDF to text 的 5 类事故

事故 表面看起来 生产里会坏在哪里
标题层级丢失 文本还在 检索命中后不知道属于哪个产品、版本或步骤
表格结构丢失 表头和数字都被抽出来了 Agent 可能把字段含义和数值错配
页码缺失 仍能生成答案 citation 无法回到原文页
bbox 缺失 页面级引用还能写 视觉定位、截图复核、法务审计都没法做
doc_version / source_fingerprint 缺失 当前样本能跑 版本变更后坏案例无法复现

4. Week7 和 Week8 的分界线

Week7 只做索引前的数据资产准备：

  • parse
  • normalize sections
  • chunking
  • evidence anchors
  • quality report
  • Week8 ready gate

Week8 才做：

  • embedding
  • pgvector / search index
  • hybrid retrieval
  • reranker
  • RAG API
  • citation rendering

如果 Week7 抢跑 Week8，会让课程主线变乱：学生还没有可验收 chunk，就开始讨论检索效果。

5. 一个合格 document asset 最少保留什么

字段 为什么必须保留
source_fingerprint 确认解析的是哪一份原始字节
doc_version 支撑版本回放和策略回归
page_no PDF citation 的最小条件
bbox / bbox_missing_reason 支撑位置回指或解释为什么没有 bbox
section_path 保留标题层级和上下文
parse_strategy_version 解析策略可复现
chunk_strategy_version chunk 策略可回归
quality_flags 告诉 Week8 哪些内容可消费、哪些要隔离

更工程化一点，可以把 Document Asset v1 看成四组字段：

字段组 代表字段 判断问题
Identity source_id、doc_id、source_fingerprint、doc_version 这到底是哪份文档、哪一版、哪一次原始字节？
Structure section_id、section_path、section_type、chunk_id 文档结构是否还在，chunk 是否能继承上下文？
Location page_no、bbox、bbox_missing_reason、source_url 答案能否回到原文位置，不能回指时原因是否诚实？
Control parse_strategy_version、chunk_strategy_version、quality_flags、allowed_for_indexing 策略能否回归，质量是否允许进入 Week8？
Note小白视角

如果把文档当成“证据”，Document Asset v1 就是在给证据贴标签：来源、位置、版本、结构、质量和是否允许被检索。

6. OmniSupport 里的三个文档场景

文档 为什么适合 Week7 重点风险
Northstar Edge Gateway 安装手册 有步骤、表格、错误码和页码，适合训练 structure-aware chunking 步骤被切断或错误码和修复建议分离
Workspace Help Center 有 HTML/Markdown 风格层级，适合训练 section_path 和 source_url 没有 bbox 时必须写清 not applicable
Release Notes 有版本、产品线、变更说明，适合训练 doc_version 与 source_fingerprint 版本混淆会导致 Week8 引用错 release
场景 本周最小动作 下游怎么用
安装手册 PDF 保留 page、bbox、表格和步骤边界 Week8 引用具体页码，Week11 检查答案是否引用正确证据
Help Center HTML / Markdown 保留 source URL、heading path、段落类型 Week8 能按主题检索，citation 回到具体帮助页或章节
Release Notes 保留版本、发布时间、产品线、source fingerprint Week8 不把旧版本事实当成当前答案

7. 生产反模式

反模式 为什么危险 正确做法
只保留 text 下游无法回源、无法复盘 至少保留 source、version、section、page/bbox、策略版本
chunk 无来源 citation 只能靠猜 chunk 必须关联 evidence anchor
parser 输出无版本 解析策略升级后 ID 和质量不可比较 写入 parse_strategy_version
质量不达标却进入 Week8 坏 chunk 会变成检索噪声 只有 allowed_for_indexing=true 才能索引

小白问答

问题 回答
为什么不先把 PDF 都转成 Markdown？ Markdown 可以是中间表示，但不能替代 source fingerprint、page、bbox、section、quality gate。
没有 bbox 的文档是不是都不能用？ 不是。HTML / Markdown 可以写 not applicable，但 PDF 缺 page 或 bbox reason 就不能装作没问题。
citation 能不能让 LLM 根据上下文写？ 不能。LLM 只能消费已经存在的 evidence anchor，不能发明来源。
Week7 为什么不做 embedding？ 因为 embedding 会放大输入质量问题。先让文档资产合格，再进入 Week8 索引。

课堂练习

给你一份 parsed output，只包含：

{"text": "Reset the device and retry provisioning."}

请判断它是否能进入 Week8，并写出至少 5 个缺失字段。参考答案应该包含：doc_id、source_fingerprint、doc_version、section_path、page_no 或 bbox_missing_reason、parse_strategy_version、chunk_strategy_version、evidence_anchor。

本课最重要判断

Week7 的输出不是“更多文本”，而是 带结构、证据和质量状态的文档资产。

  • JSON Schema：https://json-schema.org/understanding-json-schema/。Week7 的 section、chunk、anchor 都应该先有 schema 边界。
