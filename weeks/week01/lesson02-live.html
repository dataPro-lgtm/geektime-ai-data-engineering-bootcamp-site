交付标准不是感觉题

Lesson02 · 可签字交付

知识库问答 + 工单联动，什么时候才算真正 Done？

这一讲不是继续追求“更像人回答”，而是先把业务、架构、合规、运维四个角色都能签字的条件讲清楚。

从这一讲开始，课程主线正式从“事故诊断”转入“交付标准”。后面 14 周学的每一层能力，都是在给这些签字条件补证据。

开场冲突 五层 Done 签字现场 工件落地

先把课堂重心拉回来：这一讲不是技术实现课，而是一次“签字课”。 学员要先接受判断框架，后面工具、数据、评测和治理才有共同目标。

一句话判断

本讲唯一主判断
Done 不是“能回答”，而是
业务敢验收、质量能门禁、安全有边界、运行可降级、治理可追责。
只要这五层里还有一层站不住，项目就还停留在“能演示”，没有进入“可交付”。

这一页先讲结论，不展开术语。 后面所有案例、图和工件，都只是为了证明“可签字交付”这句话。

判断框架

开场冲突：为什么“能答”仍不能上线

POC 阶段看起来已经成功

  • 能回答账户冻结、额度调整、账单问题等常见 FAQ
  • 能从知识库里生成解释
  • 能调用工单接口发起申请
  • 业务方会说：“看起来已经能用了”

一进试点就没人敢签字

  • 回答引用旧版本业务规则
  • 没有按用户等级区分适用建议
  • “建议建单”和“自动建单”没有分层
  • 缺少证据锚点，主管无法复核
  • 坏例无法精确回放

不要让学员把问题理解成“效果还不够好”。 这页要把矛盾翻出来：现场能答，只说明局部成立；上线要签字，说明系统必须进入另一套判断。

Demo vs Production：中间差的是签字条件

认知转轴图

从 Demo 到 Production，中间差的不是一点工程细节，而是业务、质量、安全、运行、治理五类签字条件。

图只讲一句：项目被挡在上线前，通常不是因为模型不会说，而是因为没有定义签字条件。 讲完直接翻到“Done = 可签字交付”。

先把判断翻过来：Done = 可签字交付

认知翻转
技术团队不该再问“现在能不能答”，
而要先问“今天上线谁会拦我”。
真正的交付判断，不是系统会不会说，而是业务、架构、合规、运维四个角色有没有同时获得可签字证据。

这是 Lesson02 的翻转点。 这里把学员从“功能思维”切到“签字条件思维”。

五层 Done：这五层要一起站住

交付标准总图

企业 AI 的 Done 从来不是单条效果指标，而是业务、质量、安全、运行、治理五层标准同时站住。

这一页先让学员看到全图，不要逐条念。 重点是“跨角色、可审计、可追责”，不是“加更多 checklist”。

五层 Done：先看前三个签字问题

01 业务层

  • 改善什么业务结果
  • 谁来签字
  • 灰度范围和失败容忍度

02 质量层

  • 评测集 / 坏例池
  • 阈值和门禁
  • 变更后能否稳定回归

03 安全层

  • PII 和权限边界
  • 动作分级是否前置
  • 哪些动作必须进 HITL
先看前三层
业务、质量、安全先站住，系统才有资格继续谈运行和治理。

这页讲法要像“签字顺序图”，不是“知识点列表”。 先让学员把前三个签字问题记住，再进入运行和治理两层。

五层 Done：再补后两层，系统才算能负责

04 运行层

  • 失败时能否降级
  • 告警和回滚是否存在
  • 成本、延迟是否有目标

05 治理层

  • 数据 / 索引 / Prompt / 评测版本
  • 上线与回滚链路
  • 出问题后能否追责
一句话收口
只要这五层里还有一层站不住，就不能把“能答”当成“Done”。
后面 14 周不是给系统堆功能，而是在给这 5 个签字问题逐层补证据。

这页补运行层和治理层。 讲法上要提醒学员：企业 AI 的 Done 从来不是单条效果指标。

四角色签字板：先看业务和架构为什么会拦你

业务方

看结果

先问什么
  • 目标场景和成功指标是什么
  • 灰度范围和失败容忍度是什么
如果没有证据
  • 看起来有用，也不会直接验收

架构方

看链路

先问什么
  • 数据、索引、Prompt、工具能否持续演进
  • 契约、版本、回放链路是否稳定
如果没有证据
  • 系统能跑，也不给生产准入

这一页先讲业务和架构。 先把“签字不是技术团队单方面说了算”这件事立住。

四角色签字板：再看合规和运维为什么会拦你

合规 / 风控

看边界

先问什么
  • PII、权限、动作分级是否前置
  • 哪些必须拒答，哪些必须 HITL
如果没有证据
  • 人工兜底没写成规则，就不会放行

运维 / SRE

看兜底

先问什么
  • 故障能不能定位、降级、回滚
  • 健康阈值和告警规则是什么
如果没有证据
  • 演示越顺，运行时越没人敢兜底

这页补完另外两个角色。 只要有一个角色不敢签字，系统就还没有真正做完。

OmniSupport 一进评审会：先看业务和架构在看什么

业务

先问效果

第一句追问
  • 首问解决率和建单负担真的会改善吗
真正证据
  • 目标场景、成功指标、试点范围
不满足时
  • 延后上线，先补验收口径

架构

先问可演进

第一句追问
  • 数据、索引、Prompt、工具链能不能持续演进
真正证据
  • 版本、契约、可回放链路
不满足时
  • 不给生产准入

这一页先落到业务和架构两个视角。 让学员看到“第一句追问”和“真正证据”之间的区别。

OmniSupport 一进评审会：再看合规和运维在看什么

合规

先问边界

第一句追问
  • 哪些问题必须拒答，哪些动作必须 HITL
真正证据
  • PII 规则、权限边界、证据引用要求
不满足时
  • 要求补边界后再评审

运维

先问兜底

第一句追问
  • 失败时怎么降级，变更后怎么回滚
真正证据
  • 健康检查、告警、降级与回滚策略
不满足时
  • 只能灰度，不允许放量
案例定位
OmniSupport 在这门课里不是主角，而是验证器。
它的价值不是展示一个花哨 Demo，而是把签字现场真正需要看的证据都逼出来。

三个课堂工件：最后落成三张表

工件 1

交付标准记分卡
  • 先把场景、目标、指标、状态写清
  • 先对齐签字口径
  • 它是后续工程动作的上游

工件 2

风险边界清单
  • 把边界写成系统开关
  • 它是动作分级入口

工件 3

质量门禁表
  • 把指标、阈值、评测集、回退动作写出来
  • 从“看起来不错”切到“门禁过没过”

这一页的目的，是把 Lesson02 从“观念课”收口成“模板课”。 让学员看到：今天下课不是只带走观点，而是带走三张可以开工的表。

模板 1：先把交付标准记分卡写起来

交付标准记分卡

template scene / goal / metrics / status

  • 先把“签什么”写清楚
  • 再谈后面的工程动作
scene: "客服问答 + 建单联动"
business_goal: "减少重复查询"
success_metrics:
  - "FAQ 首问解决率"
  - "建议建单采纳率"

这页只需要给学员模板感。 重点不是逐行念，而是让他们知道第一张表要写到什么程度。

模板 2：再把风险边界清单写出来

风险边界清单

template 适用用户 / 禁止场景 / 证据要求 / 禁止自动执行

  • 先把系统行为边界写成规则
  • 它不是法务附录，而是系统行为开关
## 业务验收口径 & 风险边界清单
- 适用用户：客服 / 值班主管
- 禁止场景：高风险账户操作
- 证据要求：制度解释 / 规则口径
- 禁止自动执行：额度修改

告诉学员：第二张表就是把边界写成规则。 只要这张表空着，工具层就不该放量。

模板 3：最后把质量门禁表补齐

质量门禁表

template metric / threshold / eval_dataset / fallback_action

  • 把“看起来不错”切成“门禁过没过”
  • 把失败后的 fallback 也一起写清
metric: "FAQ 首问解决率"
threshold: ">= 72%"
eval_dataset: "客服坏例池 v1"
fallback_action: "降级到知识检索"

第三张表补的是质量门禁。 到这里学员才会真正理解：Lesson02 不是观念课，而是模板课。
